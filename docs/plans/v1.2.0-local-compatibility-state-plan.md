# v1.2.0 Local Compatibility State Plan

Status: active execution plan for parent issue
[#126](https://github.com/HiroLiang/tentserv-agent/issues/126) and child issues
[#127](https://github.com/HiroLiang/tentserv-agent/issues/127) through
[#130](https://github.com/HiroLiang/tentserv-agent/issues/130). Maintenance
issue [#131](https://github.com/HiroLiang/tentserv-agent/issues/131) is an
implemented and validated runtime-lifecycle prerequisite whose merge remains
required before `#127` implementation resumes.

Milestone: `v1.2.0`

Project: `Tentgent Roadmap`

## Planning Baseline

This plan and its active-plan routing must land on `main` before implementation
branches begin. Each child issue branch should start from a `main` revision that
contains this baseline.

Branch scope, branch name, and the detailed implementation plan remain
issue-specific decisions. If an issue-level decision materially changes the
approved release scope or execution order, update this plan in that issue's
branch instead of leaving the planning baseline stale.

## Outcome

This slice turns the existing partial support-proof tuple into complete,
durable local compatibility evidence and applies that evidence consistently to
local model and LoRA adapter execution.

A successful or failed result for one model, capability, backend, runtime,
profile, platform, adapter, or request shape must not authorize an unrelated
tuple.

## Current Baseline

Tentgent already has:

- the `verified`, `failed`, `supported`, `unknown`, `unsupported`, and `stale`
  support-status vocabulary;
- file-backed tuple-aware proof paths that allow some backend and runtime
  variants to coexist;
- a legacy latest-proof path kept for compatibility;
- runtime-profile-aware local server-start gates and launch proof recording;
- runtime-execution proof recording for resolved local attempts;
- Cluster route readiness, execution gates, and runtime ownership;
- request-time LoRA adapter selection for supported local chat paths.

The current proof key and domain record still cover only a subset of the
contracted tuple. Adapter identity, complete platform/runtime identity, and
normalized input/output shape are not yet enforced as one complete proof
identity. Legacy evidence can therefore be more general than the execution
decision that consumes it.

## Scope

The `v1.2.0` slice includes:

- one kernel-owned normalized compatibility tuple;
- schema-versioned proof v2 records and deterministic exact-tuple keys;
- coexistence and exact replacement of unrelated tuple proofs;
- conservative reads and migration behavior for incomplete legacy proof;
- tuple-aware local model-bound server and Cluster gates;
- tuple-aware LoRA adapter proof identity and serving gates;
- exact-tuple proof filtering and clearing;
- consistent model, adapter, server, Cluster, doctor, CLI, and daemon REST
  diagnostics;
- sanitized persisted runtime failures;
- contract, user documentation, version-note, and regression-test closeout.

## Non-Goals

This slice does not include:

- dynamic backend or runtime candidate selection;
- automatic fallback across routes, models, or runtimes;
- provider Cluster target execution;
- GPU, CPU, or memory scheduling;
- automatic multimodal context assembly;
- provider tool or function-call orchestration;
- cloud rerank providers;
- OpenShell broker or gateway auth;
- shared compatibility registry publication or consumption;
- model conversion or generated metadata automation;
- a broad repository-wide SQLite migration;
- new model runtime or backend families;
- fixed model-plus-adapter Cluster bindings;
- managed LoRA training-plan or runner redesign;
- publishing the `v1.2.0` tag, GitHub Release, release artifacts, or Homebrew
  tap update.

## Release Boundary

The `v1.2.0` milestone names this product capability slice. Issue `#130`
updates version notes and release-readiness coverage, but issues `#126`-`#130`
do not publish a tag, GitHub Release, artifacts, or Homebrew formula.

If `v1.2.0` will be distributed after this slice is accepted, create a separate
release issue after `#130` so publication credentials, native artifacts,
checksums, signing/notarization, and tap updates do not widen the compatibility
implementation branches.

## Required Invariants

- Local proof is authoritative for the exact local tuple it observed.
- Static model and adapter metadata remain hints, not runtime proof.
- A positive hint cannot hide a current applicable local failure.
- Missing legacy dimensions never become precise `verified` authorization.
- Unrelated tuple proofs coexist and are not replaced or cleared together
  unless the caller explicitly selects the capability-wide bulk operation.
- `verified` and `supported` remain allowed by the current covered gates.
- `failed` and `unsupported` remain blocked.
- `unknown` and `stale` require the existing explicit `allow_unverified`
  policy where that policy is already supported.
- No gate silently changes the selected model, adapter, backend, runtime, or
  request shape.
- Existing stable CLI and daemon REST behavior remains backward compatible;
  new proof-detail surfaces stay additive or experimental.

## Slice 1: Complete Tuple And Proof v2

Issue: [#127](https://github.com/HiroLiang/tentserv-agent/issues/127)

Deliver:

- normalized identity for model, capability, format, quantization, backend,
  runtime family/package/version, runtime profile/version, platform/device,
  optional adapter/load identity, and input/output shape;
- deterministic proof keys derived from every execution-affecting dimension;
- proof v2 serialization and atomic file-backed persistence;
- exact-tuple coexistence, replacement, listing, filtering, and removal ports;
- dual reads for proof v2, the current tuple-aware subset, and legacy
  latest-proof records;
- conservative `stale` resolution when required legacy dimensions are absent;
- normalization, collision, coexistence, migration, and concurrent-write
  tests.

Do not add user-facing hard gates in this slice.

## Slice 2: Local Model And Cluster Gates

Issue: [#128](https://github.com/HiroLiang/tentserv-agent/issues/128)

Deliver:

- complete support queries for model-bound server start and Cluster readiness
  and execution;
- exact backend, runtime, package, profile, platform/device, and endpoint-shape
  comparisons;
- unchanged allow/block policy for effective support status;
- complete `server-start` and `runtime-execution` success and failure proof;
- no proof writes for lookup, validation, unsupported input, or cloud-provider
  failures;
- tuple-specific server and Cluster blocker diagnostics;
- regression coverage proving that unrelated backend, runtime, profile, and
  shape evidence cannot authorize execution.

Direct one-shot commands retain their current compatibility boundary and do
not gain a new hard gate unless separately approved.

## Slice 3: LoRA Adapter Proofs And Gates

Issue: [#129](https://github.com/HiroLiang/tentserv-agent/issues/129)

Deliver:

- adapter proof identity containing adapter ref, base model, target capability,
  runtime identity, platform/device, selected weight identity, load-affecting
  configuration, and relevant shape;
- tuple-aware request-time adapter checks shared by direct model-bound and
  Cluster serving;
- exact successful and failed adapter-bound runtime proof recording;
- staleness when adapter content, selected weight, base binding, runtime
  package, or load-affecting configuration changes;
- adapter-specific blocker and recovery diagnostics;
- regression coverage across adapter, base model, backend/runtime, weight, and
  configuration differences.

A successful training run remains provenance, not serving verification.
The detailed `#129` plan must enumerate the existing LoRA serving workflows and
capabilities it gates. Any adapter family or media/job workflow that is not
exercised by the approved serving path must remain explicitly unsupported or
deferred instead of being implied verified by a chat-serving proof.

## Slice 4: Diagnostics, Recovery, And Closeout

Issue: [#130](https://github.com/HiroLiang/tentserv-agent/issues/130)

Deliver:

- compact list output with complete tuple data reserved for inspect/detail

- exact-tuple proof filtering and clearing;
- an explicit backward-compatible capability-wide bulk clear operation;
- evidence source, stale reason, failure reason, and a copyable next action;
- compacted, redacted, and bounded persisted runtime errors;
- cross-surface status conformance and release-readiness coverage;
- updated contracts, user commands, version notes, active roadmap routing, and

## Decisions Deferred To Issue Planning

Before implementation begins on the applicable issue, its detailed plan must
settle:

- the proof v2 serialized schema marker and exact legacy dual-read or
  dual-write transition;
- canonical serialization for normalized input/output shape;
- the authority for runtime package and platform/device version facts;
- adapter content and selected-weight identity;
- which adapter scale or configuration values affect the proof key;
- proof retention and audit behavior after adapter removal or rebind;
- the exact LoRA serving workflows and capabilities covered by `#129`;
- additive CLI and REST shapes for exact-tuple filtering and clearing;
- the smallest fixture matrix that proves tuple isolation without requiring
  provider network access.

These decisions should be made inside the selected child issue, not by widening
the parent tracking issue.

## Validation Gates

Each child issue should run focused tests for its changed kernel, CLI, daemon,
and Python runtime boundaries. The final closeout should run:

```bash
cargo fmt --all -- --check
cargo check --workspace
cargo test --workspace
uv run --project python/tentgent-model-runtime pytest
bash scripts/test-release-readiness.sh
git diff --check
```

Fixture coverage must include unrelated tuples that differ by backend/runtime,
profile version, platform/device class, request shape, adapter, and selected
adapter weight or load configuration where applicable.

Synthetic platform/device facts may prove resolver isolation for platforms not
available in CI. They must not create or claim successful local verification
for a platform/device tuple that was not actually executed on that machine.
Live smoke proof remains scoped to the host and runtime that produced it.

## Branch Planning Boundary

This plan does not create or prescribe branch names. After the execution order
is accepted, select one child issue, agree on the branch scope and name, and
then develop that issue's detailed implementation plan. One branch should
normally carry one child issue as a vertical slice. Create the branch only
after the user confirms the proposed branch target.

## Completion

The `v1.2.0` slice is complete when:

- prerequisite issue `#131` is closed with model release and runtime restart
  evidence;
- issues `#127`-`#130` are closed;
- parent issue `#126` reports all sub-issues complete;
- exact tuple isolation and conservative legacy behavior are proven;
- model, adapter, server, Cluster, doctor, CLI, and REST decisions agree;
- stable workflows remain backward compatible;
- required contracts and user documentation match implementation;
- the full validation gates pass;
- deferred work remains routed in `v1.x-roadmap.md`;
- this plan is archived and the active plan index is updated.

Release publication, artifact signing, and Homebrew updates require their own
accepted release issue and are not implied by closing parent issue `#126`.
