# v1.x Roadmap

Status: active long-term product roadmap after the `v1.0.0` stability release.

This roadmap tracks post-1.0 product evolution. It is for new capabilities,
architecture direction, and version-sized feature slices. Bug fixes, release
follow-up, and documentation cleanup belong in
[bugfix-maintenance-plan.md](./bugfix-maintenance-plan.md).

## Purpose

`v1.0.0` froze the documented stable compatibility promise. The `v1.x` line
should now add capabilities without weakening that promise:

- keep stable CLI and daemon REST behavior predictable
- keep provider-compatible support explicit and partial where documented
- make model, adapter, backend, runtime profile, and platform compatibility
  explainable before routing grows more dynamic
- add multi-model serving only when each configured route can be validated and
  inspected

## Roadmap Principles

- Keep the product surface CLI plus daemon REST.
- Prefer vertical feature slices that carry one operator-visible capability
  through contracts, domain behavior, entry points, docs, and tests.
- Keep native Tentgent request intent separate from provider-shaped payloads.
- Treat static model and adapter metadata as hints, not proof.
- Treat local verification on this machine as authoritative. Shared or built-in
  records can provide hints, but they must not replace local evidence.
- Avoid hidden fallback to another model, backend, provider, or generated
  metadata when a configured capability is missing.
- Keep large artifacts in filesystem stores; add indexed metadata only when it
  improves compatibility, proof, routing, or query behavior.

## v1.1.0 Delivered: Cluster MVP

Issues `#113`-`#118` delivered the first multi-model local serving foundation:

- named Cluster definitions stored as canonical TOML under
  `TENTGENT_HOME/clusters/<cluster-ref>/cluster.toml`;
- validated `chat`, `embedding`, `rerank`, `audio-transcription`, and
  `vision-chat` route targets;
- read-only readiness and ownership diagnostics through Cluster inspect and
  doctor summaries;
- one Cluster server using the existing server lifecycle and provider-shaped
  compatibility ingress;
- dynamic request-time adapter selection through the existing native local
  server boundary;
- cross-process resource coordination, structured mutation blockers, durable
  runtime ownership, guarded hot reload, bounded shutdown drain, and stale
  ownership reconciliation.

Provider targets remain definition-valid but execution-unsupported. Automatic
cross-route fallback, automatic multimodal context assembly, fixed adapter
bindings, a shared scheduler, and SQLite migration were not part of v1.1.0.

The completed execution records are archived in
[archive/cluster-roadmap.md](./archive/cluster-roadmap.md). New sessions should
start from this roadmap and the current contracts, not from the archived
implementation handoff.

## v1.2.0 Active: Local Compatibility State

Parent issue
[#126](https://github.com/HiroLiang/tentserv-agent/issues/126) and child issues
[#127](https://github.com/HiroLiang/tentserv-agent/issues/127) through
[#130](https://github.com/HiroLiang/tentserv-agent/issues/130) select the next
vertical slice from the compatibility foundations below.

The slice delivers:

- a complete normalized local compatibility tuple and proof v2 persistence;
- conservative migration of incomplete legacy proof;
- exact-tuple local model-bound server and Cluster gates;
- tuple-aware LoRA adapter serving proof and authorization;
- consistent inspect, doctor, recovery, CLI, daemon REST, documentation, and
  regression-test closeout.

Dynamic routing, automatic fallback, scheduling, provider Cluster execution,
multimodal context assembly, provider orchestration, shared registries,
conversion, and new runtime families remain outside `v1.2.0`.
Closing issues `#126`-`#130` completes the capability slice; publishing the
`v1.2.0` tag, signed artifacts, GitHub Release, and Homebrew update requires a
separate accepted release issue.

The execution order, coverage matrix, validation gates, and issue-specific
decision boundaries are defined in
[v1.2.0-local-compatibility-state-plan.md](./v1.2.0-local-compatibility-state-plan.md).

## Later Compatibility Foundations

The completed Cluster MVP now provides the baseline for compatibility work in
later `1.x` slices:

- durable local compatibility proof storage for model, capability, backend,
  runtime package, platform/device class, adapter, and input/output shape
- tuple-aware model and LoRA compatibility gates so one successful adapter or
  model launch is not trusted for unrelated tuples
- actionable inspect and doctor output for verified, failed, stale, unknown, and
  unsupported local tuples
- bounded dynamic runtime routing where candidate attempts are documented,
  cached, and inspectable
- resource coordination for model mutation, adapter writes, conversion, cache
  updates, warm server ownership, and GPU/CPU/memory-sensitive jobs

## v1.x Module Flow

Use this flow to decide whether new work belongs in a later `1.x` feature
release or the maintenance plan. The `v1.1.0` column records what was delivered
or intentionally deferred.

| Module | Role In The System | v1.1.0 Outcome | Later Direction |
| --- | --- | --- | --- |
| Bugfix And Maintenance | Patch fixes, stale docs, diagnostics polish, release follow-up, and repository hygiene for already released behavior. | Tracked separately. | Continue in [bugfix-maintenance-plan.md](./bugfix-maintenance-plan.md); move work here only when it adds a public surface or version-sized design. |
| Cluster System | User-facing named routing object for `chat`, `embedding`, `rerank`, `audio-transcription`, and `vision-chat`. | Delivered as experimental definitions, readiness, native local routing, dynamic adapter compatibility, and lifecycle reuse. | See the [archived Cluster roadmap](./archive/cluster-roadmap.md); extend only through a new accepted vertical slice. |
| Compatibility State System | Route readiness, proof concepts, tuple-aware model/LoRA gates, support status, runtime profiles, and runtime failure evidence. | Delivered the Cluster-required readiness and existing proof integration; no SQLite migration. | The active `v1.2.0` slice adds complete file-backed tuple proof and exact model/LoRA gates; broader indexed storage remains incremental later work. |
| Runtime Resource System | Delete protection, active route ownership, cancellation, shutdown, cleanup, and resource gates. | Delivered cross-process transition locks, structured blockers, durable runtime ownership, hot reload drain, and reconciliation. | A broader GPU/CPU/memory scheduler remains a separate later feature. |
| Dynamic Runtime Routing | Bounded backend/runtime selection when one model may use multiple runtime families. | Deferred. Cluster routes remain explicit and do not silently fall back. | Keep attempts bounded, cached, and inspectable when a future slice is accepted. |
| Multimodal Context System | Convert files, images, audio, or video into bounded context artifacts before chat dispatch. | Deferred. Cluster exposes separate media routes only. | Build on explicit Cluster routes and ownership; do not hide conversion or fallback. |
| Provider Orchestration System | Provider tool/function-call mapping, provider-specific extensions, and cloud rerank adoption. | Deferred. Provider Cluster targets are definition-valid but execution-unsupported. | Keep provider-shaped behavior explicit at ingress and egress. |
| External Trust And Conversion System | OpenShell broker auth, shared compatibility registry, explicit model conversion, and generated metadata provenance. | Deferred. | Local verification remains authoritative; conversion must be an explicit user action. |

## Later 1.x Work

These directions were intentionally kept out of `v1.1.0` and require a later
planning pass to narrow them into a verifiable vertical slice:

- automatic multimodal context assembly for files, images, audio, and video
- provider-compatible tool and function-call orchestration
- cloud rerank as an explicit provider or adapter family
- OpenShell-managed provider gateway or broker auth boundaries
- shared compatibility registry publish/consume behavior
- explicit conversion and metadata-generation workflows with provenance
- broader direct media server wrappers and typed streaming contracts beyond the
  already stable route families

## Issue Planning Rules

- Put feature and architecture issues here when they change product capability
  or public workflow shape.
- Put patch fixes, stale docs, release follow-up, and diagnostics polish in
  [bugfix-maintenance-plan.md](./bugfix-maintenance-plan.md).
- Use milestones for release targeting, such as `v1.1.0` or `v1.2.0`.
- Use the GitHub Project board for status, priority, area, and work type.
- Archive or rewrite this plan when its main tracks are completed or
  superseded.
